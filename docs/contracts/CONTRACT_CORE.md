# Lode Core Model Contract

This document defines the **core data model** and invariants for Lode.
It is authoritative for all implementations and adapters.

Lode defines persistence structure only. It does not define execution,
planning, scheduling, or optimization.

---

## Goals

1. Immutable, self-describing snapshots.
2. Explicit, persisted metadata.
3. Linear history per dataset.
4. Backend-agnostic layout semantics.

---

## Non-Goals

- Query planning or execution.
- Background compaction or mutation.
- Backend-specific behavioral flags.

---

## Core Entities

### Dataset
A dataset is a logical collection of snapshots and has a stable
`DatasetID`.

### Snapshot
A snapshot records the immutable state of a dataset at one instant. Each
snapshot has a stable `SnapshotID` and, optionally, a parent snapshot ID.

### Snapshot ID
Lode generates every snapshot ID, for Datasets and Volumes alike, and
callers never choose one. Since v0.11.0 an ID has the form `<instant>-<nonce>`:

- `<instant>`: the Unix time, in nanoseconds, at which the write begins,
  expressed in decimal without a sign or leading zero.
- `<nonce>`: sixteen lowercase hexadecimal digits from a cryptographically
  secure random source.

Uniqueness does not depend on the clock. Two IDs coincide only when two
writes begin in the same nanosecond *and* draw the same 64-bit nonce. The
probability is 2⁻⁶⁴ for each such pair, however often the clock repeats or
moves backward. Lode does not reserve IDs against existing ones. If IDs
nevertheless coincide while the earlier snapshot exists, the colliding
commit fails at its create-only manifest write. The commit advances the
pointer before it writes the manifest, so the failure occurs after the
pointer has moved.
The pointer can therefore continue to name the earlier snapshot until the
next commit replaces it, and retention rejects a tombstone that does not
describe the manifest (CONTRACT_RETENTION §Tombstone). Instant-only IDs
written before v0.11.0 collided whenever two writes began in the same
nanosecond, with the same consequences.

IDs are opaque strings to callers, and callers MUST NOT parse them as
numbers. A string comparison orders IDs by instant, because the instant has a
fixed length of nineteen digits from September 2001 until signed 64-bit
nanosecond time overflows in April 2262. Only an ID generated by a clock
set before 2001-09-09 01:46:40 UTC (and thus with a shorter instant) would
sort out of chronological order. A string comparison orders IDs with the
same instant by nonce, which does not reflect commit order.

IDs written before v0.11.0 consist of `<instant>` alone. They remain valid,
and Lode reads, selects, and retains them exactly as it does current IDs.
Lode treats an ID in either form as an ID in the *generated form*. A legacy ID sorts before
every current ID with the same instant.

### Head Pointer
This section is the only normative statement of the commit protocol. Other
contracts state their own obligations and refer to it rather than restating
it (V1_API_DECISIONS D10f).

The `latest` pointer identifies the head. A write persists its data before
its commit begins: a Dataset write persists its data files and then
commits, and `StageWriteAt` persists a Volume's blocks before the caller
invokes `Commit`. A failure while the writer persists data precedes the commit
and leaves the head unchanged. The commit itself resolves its parent,
advances the pointer with `CompareAndSwap`, and then persists its canonical
manifest followed by its partition manifests, one at a time. The commit is
complete once the writer persists its canonical manifest, and from then on
`Latest` and `Snapshot` return the snapshot. The partition manifests are an
index of the canonical manifest. A writer that terminates before persisting
all of them leaves a committed snapshot with an incomplete index, and the
unfiltered listings report that snapshot through its canonical manifest
(CONTRACT_READ_API §Listing Order and Cursors). A snapshot written before canonical
manifests were introduced has only partition manifests and is committed
when any of them is persisted. `Latest`, `Snapshot`, and retention find it
through them. Between the pointer update and the canonical
manifest the commit is *pending*: the pointer names a snapshot that has no manifest. A pending
commit whose writer terminates before persisting the manifest is
*abandoned*. No persisted state distinguishes a pending commit from an
abandoned one, so Lode treats every pointer that names a snapshot without a
manifest as a pending commit:

- A pointer can be missing or name a snapshot without a manifest after a
  pending or abandoned commit, a manual edit, or a failed `Put` while
  `lode.SingleProcess` replaces the pointer. `Latest` then selects the
  largest snapshot ID that has a manifest. If the clock moved backward, or
  two commits began in the same
  nanosecond, that selection may not be the most recent commit. A writer
  handle's `Latest` creates a missing pointer from the selection but never
  replaces an existing pointer, because replacing it would revert the head
  past a pending commit. A view (`ReadRoot.Records` or `ReadRoot.Blobs`)
  resolves the head the same way but MUST NOT create a missing pointer. A
  view never writes, so its store need not provide `CompareAndSwap`. Every
  write through a view's store (`Put`, `Delete`, or `CompareAndSwap`) MUST
  return `ErrReadOnly`.
- A new commit adopts the snapshot that the pointer names as its parent,
  whether or not that snapshot has a manifest, so the history remains
  linear. After an abandoned commit, the next snapshot's `ParentSnapshotID`
  therefore names an ID without a manifest. Readers resolving lineage MUST
  treat such a parent as the end of the explainable chain, as they treat an
  expired parent (CONTRACT_RETENTION §Lineage).
- A Volume commit requires its parent's manifest. It therefore persists a
  staged copy of its own manifest at
  `volumes/<volume_id>/staged/<snapshot_id>.json` before it advances the
  pointer. It removes the copy after it persists the canonical manifest.
  The next commit can therefore load the parent even after an abandoned
  commit.
  When the pointer update fails, the commit removes the copy only if the
  pointer names another snapshot, because a store may report a failure for
  an update that it applied. A Volume commit returns `ErrSnapshotConflict`
  only when its parent has neither a canonical manifest nor a staged copy
  (CONTRACT_VOLUME §Error Semantics).
- A dataset's first commit (one that expects no pointer) persists a staged
  copy of its manifest at `<dataset dir>/staged/<snapshot_id>.json` before it
  advances the pointer. It removes the copy after it persists the canonical
  manifest. A writer can therefore check its settings against the commit
  while it is pending (CONTRACT_WRITE_API §Settings). Later commits stage
  nothing, because a writer then checks its settings against the dataset's
  existing manifest. When the
  pointer update fails, the commit removes the copy only if the pointer
  names another snapshot, as a Volume commit does. When a writer abandons
  the first commit, the next commit reads the dataset's settings from the
  staged copy, adopts the abandoned snapshot as its parent, and removes the
  copy after it commits.
- Parent resolution selects the largest snapshot ID only when the pointer
  is missing or does not contain a snapshot ID. One content that is not a
  snapshot ID is reserved: the removal marker `lode:removed`, which
  `volume.Remove` writes (CONTRACT_VOLUME §Removal). A container that can
  be removed reads the marker as its removal, and `Latest` and parent
  resolution return `volume.ErrRemoved` instead of scanning. A Dataset
  cannot be removed this way and reads the marker as any other content
  that is not a snapshot ID.
- "Missing" means that the store reported the object as not found. When a
  read of the pointer, or of the manifest that the pointer names, fails with
  any other error, `Latest`, parent resolution, and Volume commits MUST
  return that error. They MUST NOT treat the failure as a missing pointer or
  manifest. The largest snapshot ID may name the head's parent, so selecting
  it would report an earlier snapshot as the head or fork the history.

Instant-only IDs written before v0.11.0 were subject to the same ordering
limit, and writes that began in the same nanosecond received identical IDs.
Retention never relies on the largest-ID selection (CONTRACT_RETENTION
§Head Protection).

### Manifest
A manifest is the authoritative description of a snapshot and its data
files.

---

## Manifest Requirements

Manifests MUST be **self-describing** and **persisted**.

Required fields:
- the schema name and version
- the dataset ID
- the snapshot ID
- the creation time
- an explicit metadata object (see §Metadata Rules)
- the list of files, with sizes and, when configured, checksums
- the parent snapshot ID, when applicable
- the row or event count (the total number of data units in the snapshot)
- the minimum and maximum timestamps, when data units implement
  `Timestamped` (omitted otherwise)

Optional fields:
- the codec name (omitted when no codec is configured)
- per-file statistics (present when the codec reports them through
  `StatisticalCodec`, and omitted otherwise)

Settings fields (format version 1.1.0 and later):
- `codec_description`: the codec's configuration as `Codec.Describe`
  returns it, omitted when it is empty
- `partition_keys`: the Hive partition keys in order, omitted for a layout
  without partitions
- `paths`: the names within the dataset's paths (`datasets`, `snapshots`,
  `partitions`, `segments`, `manifest`, `data`, `expired`, and `staged`),
  with `flat` true and the datasets and snapshots directories omitted for
  flat paths

With the codec, compressor, partitioner, and checksum names, these fields
record every setting a writer must share with the dataset
(CONTRACT_WRITE_API §Settings). The format version, not the presence of a
field, decides which fields a manifest records. A manifest of format
version 1.0.0 predates these fields, so Lode assumes the path names under
which it found the manifest. A manifest of format version 1.1.0 or
later without `paths` is invalid.

### Per-File Statistics

A `FileRef` MAY contain per-file statistics reported by the codec.

- Statistics are independent of any particular codec: any codec may report
  them through the `StatisticalCodec` interface.
- When a codec reports statistics, the writer MUST persist them on the
  `FileRef`.
- When a codec does not report statistics, the writer MUST omit the
  statistics field.
- Statistics values MUST be serializable as JSON.
- The writer MUST NOT infer statistics, and the codec reports them only
  from observed data.
- Per-file statistics comprise the row count and, for each column, the
  minimum, maximum, null count, and distinct count.
- The distinct count is optional, and a value of zero means that the codec
  did not compute it.

### Checksum Rules

- Checksum computation is explicit and disabled by default.
- When the caller configures a checksum component, manifests MUST record:
  - the checksum component name, and
  - a checksum value for each data file of the snapshot.
- When the caller configures no checksum component, the writer MUST omit
  checksum fields.

Manifests are immutable once written.

---

## Metadata Rules

- Metadata MUST be explicit on every snapshot.
- A writer accepts metadata as any value that encodes as a JSON object (a
  struct or a map). The writer converts `nil` to an empty object (`{}`) at
  the API boundary, and it rejects a value that does not encode as an
  object with `ErrInvalidArgument`.
- Empty metadata (`{}`) is valid, and the writer MUST persist it as an
  explicit object.
- Lode retains the persisted object as written (`Metadata`), decodes it on
  request, and does not reinterpret its values.
- Manifests always contain a metadata object. A manifest whose metadata is
  absent or not an object is invalid.

---

## History and Immutability

- Snapshot history is strictly linear, with a single head.
- Snapshots are immutable after commit.
- Data files are immutable once written.
- Commits create new state and do not mutate existing state.
- Retention, which applies to Datasets only, removes
  committed snapshots and their data files but never rewrites them.
  Retention records each expiry in a new object (a tombstone) and never
  reassigns a snapshot ID. Retention reclaims the objects of uncommitted
  writes without a record, because no snapshot ever existed ([`CONTRACT_RETENTION.md`](CONTRACT_RETENTION.md)).

## Design Invariant

> **Lode stores facts, not interpretations.**
