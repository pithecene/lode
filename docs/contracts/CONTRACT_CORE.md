# Lode Core Model — Contract

This document defines the **core data model** and invariants for Lode.
It is authoritative for all implementations and adapters.

Lode defines persistence structure only. It does not define execution,
planning, scheduling, or optimization.

---

## Goals

1. Immutable, self-describing snapshots.
2. Explicit, persisted metadata.
3. Linear history per dataset.
4. Backend-agnostic layout semantics.

---

## Non-Goals

- Query planning or execution.
- Background compaction or mutation.
- Backend-specific behavioral flags.

---

## Core Entities

### Dataset
A logical collection of snapshots. A dataset has a stable `DatasetID`.

### Snapshot
The immutable state of a dataset at a point in time. Each snapshot has a
stable `SnapshotID` and, optionally, a parent snapshot ID.

### Snapshot ID
Lode generates every snapshot ID, for Datasets and Volumes alike; callers
never choose one. Since v0.11.0 an ID has the form `<instant>-<nonce>`:

- `<instant>`: the Unix time, in nanoseconds, at which the write begins,
  expressed in decimal without a sign or leading zero.
- `<nonce>`: sixteen lowercase hexadecimal digits from a cryptographically
  secure random source.

Uniqueness does not depend on the clock. Two IDs coincide only when two
writes begin in the same nanosecond *and* draw the same 64-bit nonce, a
probability of 2⁻⁶⁴ for each such pair, however often the clock repeats or
is set back. Lode does not reserve IDs against existing ones. If IDs
nevertheless coincide while the earlier snapshot exists, the colliding
commit fails at its create-only manifest write, but only after it has
advanced the pointer (because the pointer is written before the manifest).
The pointer can therefore continue to name the earlier snapshot until the
next commit replaces it, and retention declines a tombstone that does not
describe the manifest (CONTRACT_RETENTION §Tombstone). Instant-only IDs
written before v0.11.0 collided whenever two writes began in the same
nanosecond, with the same consequences.

IDs are opaque strings to callers and MUST NOT be parsed as numbers.
Compared as strings, IDs are ordered by instant, because the instant has a
fixed length of nineteen digits from September 2001 until signed 64-bit
nanosecond time is exhausted in April 2262. Only an ID generated by a clock
set before 2001-09-09 01:46:40 UTC (and thus with a shorter instant) would
sort out of chronological order. IDs with the same instant are ordered by
nonce, which does not reflect commit order.

IDs written before v0.11.0 consist of `<instant>` alone. They remain valid
and are read, selected, and retained exactly like current IDs. An ID is in
the *generated form* when it is in either form; a legacy ID sorts before
every current ID with the same instant.

### Head Pointer
The `latest` pointer identifies the head. A commit advances the pointer
before it persists its manifests. Between those two operations the commit
is *pending*: the pointer names a snapshot that has no manifest. A pending
commit whose writer terminates before persisting the manifest is
*abandoned*. No persisted state distinguishes a pending commit from an
abandoned one, so Lode treats every pointer that names a snapshot without a
manifest as a pending commit:

- When the pointer is missing or names a snapshot without a manifest (a
  pending or abandoned commit, a manual edit, or a failed `Put` in the
  replacement of `lode.SingleProcess`), `Latest` selects the largest snapshot ID that has a
  manifest. If the clock was set back, or two commits began in the same
  nanosecond, that selection may not be the most recent commit. `Latest`
  creates a missing pointer from the selection but never replaces an
  existing pointer, because replacing it would revert the head past a
  pending commit.
- A new commit adopts the snapshot that the pointer names as its parent,
  whether or not that snapshot has a manifest, so the history remains
  linear. After an abandoned commit, the next snapshot's `ParentSnapshotID`
  therefore names an ID without a manifest. Readers resolving lineage MUST
  treat such a parent as the end of the explainable chain, as they treat an
  expired parent (CONTRACT_RETENTION §Lineage).
- A Volume commit requires its parent's manifest. It therefore persists a
  staged copy of its own manifest before it advances the pointer, so the
  next commit can load the parent even after an abandoned commit; only a
  parent without either copy makes a Volume commit return
  `ErrSnapshotConflict` (CONTRACT_VOLUME §Error Semantics).
- A dataset's first commit (one that expects no pointer) persists a staged
  copy of its manifest at `<dataset dir>/staged/<snapshot_id>.json` before it
  advances the pointer, and removes the copy after it persists the canonical
  manifest, so that a writer can check its settings against the commit
  while it is pending (CONTRACT_WRITE_API §Settings). Later commits stage
  nothing: the dataset then has a manifest to check against. When the
  pointer update fails, the copy is removed only if the pointer names
  another snapshot, as for a Volume. When the first commit is abandoned, the
  commit that adopts it as its parent, having read its settings from the
  staged copy, removes the copy after it commits.
- Parent resolution selects the largest snapshot ID only when the pointer
  is missing or does not contain a snapshot ID.
- "Missing" means that the store reported the object as not found. When a
  read of the pointer, or of the manifest that the pointer names, fails with
  any other error, `Latest`, parent resolution, and Volume commits MUST
  return that error. They MUST NOT treat the failure as a missing pointer or
  manifest: the largest snapshot ID may name the head's parent, so selecting
  it would report an earlier snapshot as the head or fork the history.

Instant-only IDs written before v0.11.0 were subject to the same ordering
limit, and writes that began in the same nanosecond received identical IDs.
Retention never relies on the largest-ID selection (CONTRACT_RETENTION
§Head Protection).

### Manifest
The authoritative description of a snapshot and of its data files.

---

## Manifest Requirements

Manifests MUST be **self-describing** and **persisted**.

Required fields:
- the schema name and version
- the dataset ID
- the snapshot ID
- the creation time
- an explicit metadata object (see §Metadata Rules)
- the list of files, with sizes and, when configured, checksums
- the parent snapshot ID, when applicable
- the row or event count (the total number of data units in the snapshot)
- the minimum and maximum timestamps, when data units implement
  `Timestamped` (omitted otherwise)

Optional fields:
- the codec name (omitted when no codec is configured)
- per-file statistics (present when the codec reports them through
  `StatisticalCodec`; omitted otherwise)

Settings fields (format version 1.1.0 and later):
- `codec_description`: the codec's configuration as `Codec.Describe`
  returns it, omitted when it is empty
- `partition_keys`: the Hive partition keys in order, omitted for a layout
  without partitions
- `paths`: the names within the dataset's paths (`datasets`, `snapshots`,
  `partitions`, `segments`, `manifest`, `data`, `expired`, and `staged`),
  with `flat` true and the datasets and snapshots directories omitted for
  flat paths

With the codec, compressor, partitioner, and checksum names, these fields
record every setting a writer must share with the dataset
(CONTRACT_WRITE_API §Settings). A manifest without `paths` was written
with format version 1.0.0, before these fields existed; it is read as using
the names under which it was found.

### Per-File Statistics

A `FileRef` MAY contain per-file statistics reported by the codec.

- Statistics are independent of any particular codec: any codec may report
  them through the `StatisticalCodec` interface.
- When a codec reports statistics, they MUST be persisted on the `FileRef`.
- When a codec does not report statistics, the statistics field MUST be
  omitted.
- Statistics values MUST be serializable as JSON.
- Statistics MUST NOT be inferred; the codec reports them from observed
  data.
- Per-file statistics comprise the row count and, for each column, the
  minimum, maximum, null count, and distinct count.
- The distinct count is optional; a value of zero means that it was not
  computed.

### Checksum Rules

- Checksum computation is explicit and disabled by default.
- When a checksum component is configured, manifests MUST record:
  - the checksum component name, and
  - a checksum value for each file written by the dataset.
- When no checksum component is configured, checksum fields MUST be omitted.

Manifests are immutable once written.

---

## Metadata Rules

- Metadata MUST be explicit on every snapshot.
- `nil` metadata is converted to an empty object (`{}`) at the API boundary.
- Empty metadata (`{}`) is valid and MUST be persisted as an explicit
  object.
- Metadata values MUST be serializable as JSON.
- Manifests always contain a non-nil metadata map.

---

## History & Immutability

- Snapshot history is strictly linear, with a single head.
- Snapshots are immutable after commit.
- Data files are immutable once written.
- Commits create new state; they do not mutate existing state.
- Retention (for Datasets only; Volume retention is deferred) removes
  committed snapshots and their data files but never rewrites them. The
  expiry of a committed snapshot is recorded by a new object (a tombstone),
  and retention never reassigns a snapshot ID. Objects of writes that never
  committed are reclaimed without a record, because no snapshot ever
  existed (`CONTRACT_RETENTION.md`).

---

## Design Invariant

> **Lode stores facts, not interpretations.**
